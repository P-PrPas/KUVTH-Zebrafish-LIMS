# KU registration and passwords

Anyone with an `@ku.th` email can register. Registration sends a six-digit email code; verification is required before a password is stored or the account can sign in. New users receive `guest` access to the central dashboard's unfiltered totals only. An admin grants `member` access in **Lab members**, using the role selector and **Save access**. Existing admin-only restrictions still apply to members.

Passwords are available only to Guests, are 8–128 characters, and use salted PBKDF2-SHA256 with 600,000 iterations. Admins and Members must use the existing email-code workflow, including its daily lock and administrator alerts. Five failed Guest password attempts lock the account for 15 minutes; locked, unknown and ineligible accounts all return the same 401 response. Existing legacy Admin/Member password hashes are preserved but cannot authorize password login. Roles remain checked on every API request.

Existing accounts keep their roles and IDs. The login page defaults to email-code login for Admin/Member; **Guest sign in with password** opens the Guest flow. Guests can reset a password after verifying their email code; this revokes previous sessions without deleting offline work. Password hashing happens only after OTP verification succeeds. Registration delivery runs as a background task with an identical public response for missing, existing and throttled email addresses. An administrator can invite an unverified active Guest as a Member; the pending registration code is invalidated and the account ID is preserved.

Deploy migration `000025_guest_password` using the existing runner. It follows main's schema 24 and also accepts databases that previously applied the redesign branch's 23: existing password columns, hashes, account IDs and sessions are retained. PostgreSQL is canonical; regenerate the MySQL scripts after schema changes. Configure SMTP and HTTPS with secure cookies. Do not roll back while Guest accounts exist: rollback refuses Guests rather than deleting them or granting Member access.

The bundled Nginx proxy limits `/auth/login` and `/auth/register` to 1 request/second per client IP with a burst of 5; OTP request/verification routes are excluded. Password derivation and password-login work are capped at two concurrent operations per API process, returning 503 when busy instead of queueing unbounded work. Keep API ports private in production and preserve the proxy's real client IP when placing it behind another trusted proxy.

If antivirus or a managed network intercepts SMTP TLS, Docker needs the same trusted root CA as the host. Verify the certificate fingerprint against the host trust store, append that public CA to the container's standard CA bundle, mount the combined bundle read-only, and set `SSL_CERT_FILE` to its container path. Keep certificate verification enabled. This machine's AVG fix uses `%TEMP%/vetku-pr43-smtp/smtp-ca-bundle.pem` and the local Compose override `%TEMP%/vetku-pr43-smtp/local-tls.json`; include that override when recreating the API container. These machine-specific files are not part of the repository.

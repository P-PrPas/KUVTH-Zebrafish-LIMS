# แผนยกระดับ UI ของระบบ Admin และคำร้อง

วันที่ตรวจ: 12 ตุลาคม 2026 · Branch: `feat/kuvacb-redesign-v2`

สถานะ: เสนอแผนเพื่อพิจารณา ยังไม่เริ่มปรับหน้าฟีเจอร์ตามแผนนี้
ข้อยกเว้นที่ผู้ใช้สั่งให้แก้ทันที: เมนู Logs กลับมายังหน้าหลักแล้ว

## ขอบเขตและหลักฐานการตรวจ

- อ่านเส้นทางและสิทธิ์ใน `frontend/src/App.tsx` พร้อมหน้า `corrections.tsx`, `imports.tsx`, `members.tsx`, `audit.tsx`, `master.tsx` และส่วน Timing ที่ App นำเข้า
- ตรวจองค์ประกอบที่เพิ่มหลังรวม main: คำร้องของ Member, การพิจารณาของ Admin, หน้าเริ่มต้น Admin, คำเชิญ/ปลดล็อก OTP/จัดการ session, งานนำเข้าทุกส่วน และลิงก์คำร้องไป Logs
- เปิดหน้าเว็บที่รันผ่าน Docker ที่ความกว้าง 1440 และ 375 พิกเซล ด้วยข้อมูลจำลอง จึงไม่ส่งอีเมล ไม่อนุมัติคำร้อง และไม่นำเข้าข้อมูลจริง
- เปิดงานนำเข้าฉบับร่างที่มี mapping, ประเด็นต้องตรวจ, ไฟล์ซ้ำ, ความต่างของต้นทาง และ deferred field โดยอ้างอิงรูปข้อมูลจาก integration tests ของ frontend
- ตรวจโค้ดสำหรับข้อขัดแย้งระหว่างคำร้องกับข้อมูลปัจจุบัน, validation, ผลการตัดสินใจ, committed/reverted imports, bulk actions และสถานะบัญชีล็อก ไม่ได้ทดลองเขียนข้อมูลจริงในสถานะเหล่านี้
- แบบจำลองภาพ: [admin-ui-concept.html](./admin-ui-concept.html) เป็นแนวทางจัดวางและสี ตัวเลข/ชื่อเป็นตัวอย่าง ปุ่มไม่เขียนข้อมูลจริง

## สิ่งที่แก้เรียบร้อย: Logs

1. Admin เปิด Logs ได้จาก `/#audit` ใต้ “ข้อมูลอ้างอิงและระบบ” ของหน้าหลัก รวมถึงเมนูเพิ่มเติมบนมือถือ
2. `/admin#audit` และ query filters จากคำร้องยังใช้ได้ เพื่อรักษาลิงก์ย้อนหลัง
3. Member ไม่เห็น Logs และไม่ร้องขอ API ของหน้า Audit เมื่อเปิด `/#audit` โดยตรง
4. ซ่อนกลุ่ม sidebar ที่ไม่มีรายการ สำหรับผู้ใช้ที่ไม่มีสิทธิ์
5. ไม่แก้สิทธิ์ API, ฐานข้อมูล, บัญชี หรือ session

## ทิศทางภาพรวม

คงอัตลักษณ์ของ KUVACB และดีไซน์ปัจจุบัน: เขียวเข้ม/teal, พื้นขาวอมเขียว, สีเหลืองอมเขียวของแบรนด์ และเส้นกรอบที่บางแต่เห็นชัด ใช้ Prompt สำหรับหัวข้อและ Noto Sans Thai สำหรับรายละเอียดตาม tokens ที่มีอยู่ เลขเวอร์ชัน รหัสปลา และเวลาใช้รูปแบบที่อ่านเทียบกันง่าย

ยกระดับความรู้สึกผ่านสัดส่วนและคุณภาพรายละเอียด: page heading ที่เหมือนกัน, พื้นที่ว่างมีจังหวะ, ตารางที่อ่านสแกนได้, ปุ่มหลักเพียงหนึ่งจุดในบริบทเดียว, สีบอกสถานะพร้อมข้อความ และรายละเอียดที่เปิดดูเมื่อจำเป็น

## แผนรายหน้า

### 1. หน้าเริ่มต้น Admin — ให้เห็นงานที่ต้องจัดการก่อน

**พบ:** การ์ดหกใบมีน้ำหนักใกล้กัน บางใบมีเพียงชื่อ ทำให้พื้นที่ว่างมากและคำร้องที่รอพิจารณาไม่เด่น

**เสนอ:** หัวหน้ากระชับพร้อมลิงก์กลับเว็บหลัก วางคำร้องที่รอพิจารณาเป็นงานหลัก มีจำนวนที่มาจากข้อมูลจริง แล้วจัดการ์ดทางลัดเป็นกลุ่ม “งานที่ต้องจัดการ” กับ “ตั้งค่าระบบ” เพิ่มไอคอนจากระบบเดิม คำอธิบายสั้น และ hover/focus ที่สุภาพ ไม่เพิ่มตัวเลขตกแต่งที่ API ไม่ได้รองรับ

### 2. คำร้องของ Admin — เปลี่ยนจากการ์ดยาวเป็นพื้นที่ตรวจงาน

**พบ:** ตัวกรองสถานะเต็มความกว้าง; แต่ละคำร้องแสดงรายละเอียดกับช่องเหตุผลปฏิเสธตั้งแต่ต้น แม้ยังไม่ตรวจข้อมูล; วันที่ภาษาไทยยังปรากฏแบบวันที่และเวลาอังกฤษ; บนมือถือ ลูกศรค่าเดิม→ค่าใหม่ไม่มีลำดับสายตาที่ชัด

**เสนอ:** แถบสถานะพร้อมจำนวนและค้นหาจากรายการที่โหลดแล้ว รายการสรุปแสดงรหัสรายการ ฟิลด์ ผู้ยื่น เวลา และสถานะ กดเลือกเพื่อเปิดแผงรายละเอียดข้างรายการบนจอใหญ่ และแผงเต็มความกว้างบนมือถือ

รายละเอียดแสดงค่าเดิม/ค่าที่เสนอเป็นสองช่องมีเส้นกรอบ แสดงค่าปัจจุบันเมื่อถูกตรวจแล้ว ถ้าข้อมูลเปลี่ยนหรือผิด validation ให้แสดงคำเตือนที่จุดนี้และคงการบล็อกอนุมัติ ปุ่ม “ตรวจข้อมูล” มาก่อน “อนุมัติ”; แสดงฟอร์มเหตุผลเมื่อเลือกปฏิเสธเท่านั้น การอนุมัติยังต้องยืนยันและ backend ตรวจซ้ำตามเดิม

### 3. คำร้องของฉันและฟอร์มส่งคำร้อง

**พบ:** หน้าคำร้องของฉันแสดงทุกสถานะเป็นการ์ดเต็มความสูง ไม่มีตัวกรอง; ฟอร์มส่งคำร้องเปิด inline ในหน้าที่มีฟอร์มเดิมอยู่แล้ว จึงเพิ่มความแน่นของหน้าการทดลอง/ปลา/ผลตรวจ

**เสนอ:** แท็บทั้งหมด/รอพิจารณา/จบแล้ว รายการย่อเปิดรายละเอียดได้ มีเวลาและผลตัดสินใจ รวมเหตุผลปฏิเสธให้เห็นชัด มีปุ่มถอนเฉพาะที่ยังถอนได้

ฟอร์มคำร้องใช้พื้นที่แยกที่ชัดเจน แสดงรายการที่กำลังแก้ ค่าเดิม ฟิลด์ที่เลือก และค่าใหม่ ไม่ให้สับสนกับการบันทึกตรง คงการเตือนคำร้องซ้ำและ offline พร้อม shared Toast สรุปสำเร็จ/ล้มเหลว มี empty/loading/error states ที่อ่านเข้าใจและกลับไปทำงานเดิมได้

### 4. นำเข้าข้อมูลย้อนหลัง — งานที่ต้องเปลี่ยนโครงสร้างมากที่สุด

**พบ:** ปุ่ม/แท็บหลายจุดยังเป็น native browser style; draft หนึ่งรายการใน fixture ทำให้ทั้งหน้ายาวประมาณ 4,800px บน desktop และยาวขึ้นบนมือถือ; วิธีนำเข้าหลายแบบ ข้อควรตรวจ และ raw JSON เปิดพร้อมกัน; เรียกชื่อสถานะและตารางทางเทคนิคในงานหลัก

**เสนอ:** หน้าแรกแสดงประวัติงานแบบรายการ มีชื่อไฟล์ วันที่ สถานะ จำนวนรายการ และผู้ทำเมื่อมีข้อมูลจาก API พร้อมปุ่ม “นำเข้าข้อมูล” เด่นหนึ่งปุ่ม เปิดงานแล้วใช้ขั้นตอน:

1. **เลือกไฟล์** — พื้นที่เลือกไฟล์ที่ออกแบบแล้ว ใช้ native input ที่เข้าถึงได้รองรับคีย์บอร์ด; บอกชนิดไฟล์และชีทให้ชัด
2. **จับคู่ข้อมูล** — จัด field mappings เป็นกลุ่ม และแสดงเฉพาะชนิดข้อมูล/ชีทที่เกี่ยวข้องกับงานนั้น วิธีเฉพาะทางเดิมยังเปิดได้
3. **ตรวจและแก้ประเด็น** — แยกปัญหาที่บล็อกกับคำเตือน มีตัวกรองและ bulk actions เดิม ช่องเหตุผลอยู่ติดการตัดสินใจ
4. **ตรวจสรุปและยืนยัน** — จำนวนที่จะนำเข้า ชนิดข้อมูล ความเสี่ยง/รายการข้าม และเหตุผลที่ยังยืนยันไม่ได้ ปุ่มยืนยันอยู่ในบริบทนี้และใช้เงื่อนไขเดิมทั้งหมด
5. **ผลการนำเข้า** — สถานะและผลที่เกิดจริง ลิงก์ดูรายการ/หลักฐาน และการย้อนงานที่ยังต้องตรวจ dependency ตามเดิม

ใช้แถบขั้นตอนพร้อมข้อความแทนการบังคับให้เลื่อนทั้งหน้า ไม่บังคับเริ่มใหม่เมื่อเปิด draft เก่า แสดงตำแหน่งไฟล์/ชีท/แถวในทุกประเด็น เปิดรายละเอียดต้นฉบับกับฉบับแก้ไขเป็นตารางค่าหรือ diff ที่อ่านได้ Raw JSON และ SHA-256 เก็บในรายละเอียดขั้นสูง

**Deferred fields:** แยกเป็นรายการรอดำเนินการพร้อมตำแหน่งต้นทาง แสดงชื่อฟิลด์ภาษาไทยควบคู่ข้อมูลเทคนิค เลือกรายการเพื่อเติมค่ากับเหตุผล แล้วแสดงผลบันทึกอย่างชัดเจน

### 5. สมาชิก สิทธิ์ คำเชิญ และความปลอดภัยบัญชี

**พบ:** ฟอร์มเชิญสมาชิกแสดงเต็มการ์ดก่อนรายการสมาชิก; ส่วนล็อก OTP/ส่งคำเชิญอีกครั้ง/ปิดบัญชีอาจอยู่ในแถวเดียวกัน; รายละเอียด offline/session มีพื้นที่มากเมื่อสมาชิกหลายคน

**เสนอ:** ย้าย “เชิญสมาชิก” เป็นปุ่มใน toolbar เปิดฟอร์มแยก แถวสมาชิกแสดงอีเมล บทบาท ผู้ปฏิบัติงาน และสถานะ ใช้แผงรายละเอียดสำหรับสิทธิ์, OTP lock, sessions และงาน offline แยก action ที่เปลี่ยนสิทธิ์ออกจาก action ปิดบัญชีอย่างชัดเจน

คง active/inactive tabs, self/last-admin protection, รายการงาน offline ที่บล็อกการปิดบัญชี, acknowledgement เมื่อสถานะ sync ไม่แน่ชัด, การ revoke sessions และการยืนยันก่อนทำตามเดิม ย้ายอีเมลผู้ส่งเป็นส่วนตั้งค่าที่ย่อได้ ไม่ปะปนกับการจัดการสมาชิก

### 6. ตั้งค่าห้องแล็บ เวลามาตรฐาน และ Logs

**พบ:** สองหน้าตั้งค่ามีดีไซน์เดิมที่ค่อนข้างดีอยู่แล้ว จึงต้องปรับความสม่ำเสมอมากกว่าสร้างใหม่ Logs ก็มีหัวหน้า/ตัวกรอง/empty state แบบ branch นี้อยู่แล้ว

**เสนอ:** ทำ headers/toolbars ให้ตรงกัน จัดรายการข้อมูลอ้างอิงให้สแกนง่าย; ปุ่มแก้ไขและเลิกใช้มีตำแหน่งคงที่; Timing แสดงเวอร์ชันที่ใช้อยู่กับฉบับที่จะสร้างแยกชัด เพิ่มการเปรียบเทียบค่าที่เปลี่ยนก่อนบันทึกโดยคงการสร้างเวอร์ชันใหม่และความหมายของ HPA

Logs เก็บรูปแบบหลักเดิม ปรับความสอดคล้องกับแผงรายละเอียดคำร้องและการนำเข้า แสดงข้อมูลก่อน/หลังให้เทียบง่าย และรักษาตัวกรองจาก deep links รายการที่ไม่มี metadata ต้องมีข้อความ fallback แทน `undefined`

## มาตรฐานร่วมและ motion

- ใช้ components และ tokens ใน repository; ไม่เพิ่ม UI framework หรือ animation dependency
- หัวข้อ ช่องกรอก helper text และแถบบันทึกมีระยะสม่ำเสมอ ปุ่มกับ “บันทึกโดย…” อยู่คนละกลุ่มและ wrap ได้
- ค่าเริ่มต้น: pending ใช้ amber, approved/success เขียว, rejected/error แดง, withdrawn สีกลาง พร้อมข้อความเสมอ การใช้สีไม่เปลี่ยนความหมายของตัวอ่อน “รอดแต่ผิดปกติ” ที่เป็นเหลือง
- ปุ่มชื่อกริยาชัด เช่น ตรวจข้อมูล ส่งคำร้อง ยืนยันนำเข้า; action สำเร็จ/ล้มเหลวใช้ Toast ร่วม ส่วน validation ติดกับช่องกรอก
- ใช้ transition 120–180ms เฉพาะปุ่ม/เปลี่ยนแผง/สถานะ โหลดข้อมูลให้สื่อว่ากำลังทำงาน รองรับ reduced motion ภาพ login/dashboard ยังคงนิ่งตามที่ผู้ใช้กำหนด
- มือถือใช้รายการย่อและรายละเอียดแนวตั้ง ตารางเลื่อนแนวนอนอยู่ในกรอบของมันเอง ไม่มีทั้งหน้าเลื่อนออกข้าง ปุ่มไม่ทับเนื้อหาหรือแป้นพิมพ์
- รองรับภาษาไทย/อังกฤษ ข้อความยาว การใช้ Tab/Escape/focus return และ zoom 200%

## ลำดับการลงมือที่เสนอ

1. ปรับ Admin home และองค์ประกอบร่วมของ headers/status/actions
2. ทำ Admin Requests + My Requests + ฟอร์มคำร้องให้ครบเส้นทางเดียวกัน
3. ทำ Imports + deferred fields เป็นขั้นตอน พร้อมสถานะ draft/committed/reverted และขอบเขตวิธีนำเข้าเดิม
4. ปรับ Members/Invitations/OTP/Sessions แล้วเก็บ Master/Timing/Logs ให้สอดคล้อง
5. ตรวจ desktop/tablet/mobile, ภาษา, accessibility และ regression ก่อน rebuild Docker ส่งให้ตรวจ

ไม่เพิ่ม sorting/filtering ที่อ้างว่าครอบคลุมข้อมูลทั้งระบบหาก API ยังไม่ได้รองรับ จำนวนและการค้นหาต้องบอกขอบเขตข้อมูลที่โหลด หลีกเลี่ยงการซ่อน warnings ด้วยการพับโดยไม่มีตัวบอกจำนวน

## เกณฑ์ส่งมอบ

- เปิดหน้าครั้งแรกแล้วรู้ว่าต้องทำอะไรต่อ รายการจำนวนมากไม่กลายเป็นฟอร์มยาวต่อกัน
- คำร้อง: pending/approved/rejected/withdrawn, conflict, validation error, การตรวจซ้ำก่อนอนุมัติ, เหตุผลปฏิเสธ, ถอน และ deep link ไป Audit ยังถูกต้อง
- Imports: CSV/XLSX inspection, draft resume, mapping variants, blocking/overridable issues, bulk decisions, changed sources, deferred values, confirmation, transaction safety และ revert dependency checks ยังทำงาน
- สมาชิก: invite/resend/unlock/role/session/disable และข้อจำกัด account/offline เดิมครบ
- ตรวจ 375/768/1440px ทั้งสองภาษา รวม empty/loading/error/disabled/long values และ keyboard
- ทดสอบ frontend ตามเส้นทางที่ปรับ, lint/TypeScript/build และตรวจ API contract เมื่อมีการเปลี่ยน payload (แผนนี้ไม่เสนอเปลี่ยน contract)
- ใช้ fixtures หรือฐานทดสอบสำหรับการอนุมัติ/นำเข้า/อีเมล ห้ามใช้ข้อมูลจริงในการทดสอบที่เขียนข้อมูล

- Navigation/Audit tests: 20 passed รวม 3 เคสที่เพิ่มสำหรับ main/admin Audit และการห้าม Member

- แบบร่าง HTML สลับหน้าได้ครบและตรวจที่ 1440/375px ไม่มี horizontal overflow; [ภาพตัวอย่างคำร้อง](./admin-ui-concept.png)
- Frontend lint, TypeScript และ production build ผ่าน
- Rebuild และ replace เฉพาะ frontend ใน Docker project `vetku-pr43`; API/PostgreSQL เดิมไม่ถูก restart

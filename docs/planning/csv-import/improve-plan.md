สถานะ: อนุมัติรูปแบบเอกสารแล้ว ยังไม่ได้ดำเนินการเปลี่ยน production

## ปัญหาและผลที่ต้องการ

ข้อมูลลูกค้าเก็บ V1Specimen เป็นทะเบียน `No`, `CODE`, `Specimen type`
และอ้าง CODE ผ่านคอลัมน์ CL, RT, DC, CLA ใน V1Fish ไม่ได้กรอกทะเบียนการจัดเก็บ
หรือตารางความสัมพันธ์แยก แบบฟอร์มใหม่จึงใช้วิธีเดียวกัน ลูกค้าขึ้นทะเบียนตัวอย่าง
ครั้งเดียว แล้วระบุรหัสที่เกี่ยวข้องบนปลาแต่ละตัว ระบบสร้างความสัมพันธ์ให้เอง

ไฟล์ชุดปัจจุบันประกอบด้วย experiment-template-final.xlsx,
registry-template-final.xlsx และคู่มือ v4 ทั้งชุด ตัวอ่านและขั้นตอนยืนยันนำเข้า
ยังต้องพัฒนาและทดสอบก่อนใช้จริง

## ผลกลุ่มควบคุม: ตัดออกจาก import รุ่นนี้

ตามคำยืนยันวันที่ 27 ตุลาคม 2026 รุ่น 4 ไม่มีตาราง QC/NBD/IVF ไม่มีข้อมูลตัวอย่าง
หรือคู่มือสำหรับกรอกผลกลุ่มควบคุม ตัวอ่าน v4 ต้องไม่เสนอ mapping สร้าง preview
หรือเขียน control_arm_count/historical control counts จากไฟล์ชุดนี้
หากพบตาราง QC ที่เพิ่มมา ให้แจ้งว่าไม่อยู่ในรูปแบบ v4 ไม่อ่านเป็นตารางชนิดอื่นแทน

คง API, schema และข้อมูลกลุ่มควบคุมเดิมใน backend เผื่อพิจารณาในอนาคต
ไม่ลบข้อมูล ไม่ถอด migration และไม่คืนหน้ากรอกหรือแผง QC บนเว็บในงานรอบนี้
ตัวอ่าน raw data แบบเก่าที่มีอยู่ไม่ถูกแก้ในรอบเอกสารนี้ แต่ห้ามนำการรองรับนั้น
มาเปิดทาง QC ในสัญญา v4 โดยไม่ได้รับคำยืนยันใหม่
ชื่อ treatment group เช่น Control ยังคงใช้ได้และไม่ใช่ข้อมูลยอด QC

## ส่วนที่ระบบมีแล้ว

ตรวจจากโค้ด main ที่ 6942201 และโค้ดใน workspace ไม่ใช่การยืนยันรุ่นที่รันบน VPS:

- ตาราง specimen และ specimen_fish_link รองรับทะเบียนและการเชื่อมหลายปลา
- API รายละเอียดปลา ส่ง specimens กลับมา และมี GET/POST /fish/{id}/specimens
- Import มีขั้นตอน confirm-fish-specimens และ export มีชีท 10_Specimens
- หน้าทะเบียนปลายังไม่มีช่องกรอกหรือแสดง CL/RT/DC/CLA
- API สร้าง specimen เดิมผูก cloneFishId กับปลาที่เปิดอยู่ จึงต้องตรวจความหมาย RT/DC
  ก่อนนำ API นี้มาใช้กับฟอร์มใหม่ ไม่ตีความ cloneFishId เป็นแหล่งเนื้อเยื่อทุกกลุ่ม
- วันที่เก็บ วันที่แช่แข็ง และอุณหภูมิเป็นข้อมูลเสริม ไม่จำเป็นต้องถอดออกจากฐานข้อมูล

## งานที่ต้องทำ

### 1. ตัวอ่านไฟล์และ dry-run

เพิ่มการตรวจ template_kind/template_version ตาม current/FORMAT.md
รับ experiment และ registry รุ่น 4 ในตัวอ่านสัญญาใหม่นี้ ไม่เดารุ่นจากชื่อไฟล์
แผ่นงานข้อมูลการทดลองมีเฉพาะ Lots A12:N62 และ Aggregate A67:AQ117
ไม่เปลี่ยนการอ่าน d1-d370 ให้คำนวณวันจาก DOB

อ่านทะเบียนตัวอย่างเพียงตาราง Specimens: A7:C207; No ไม่ใช่คีย์
CODE เป็น specimen_code และ Specimen type แปลงเป็นรหัสวัสดุที่ระบบรองรับ
อ่านกลุ่มจากส่วนต้น CODE โดยจับ CLA ก่อน CL และคงรหัสต้นฉบับไว้แสดงผล
ใช้ trim/case-insensitive comparison สำหรับตรวจซ้ำและจับคู่ พร้อมแสดงค่าต้นฉบับ
ใน preview ไม่รวมรหัสที่สะกดต่างกันโดยไม่มีการตรวจสอบ

อ่าน CL/RT/DC/CLA จากแถว OUTCOME ของปลา แล้วสร้างรายการ specimen_fish_link
โดยตรง ไม่ขอให้ลูกค้ากรอก Links หรือ source_type/source_code เพิ่ม
ตัวอย่างที่ขึ้นทะเบียนแต่ยังไม่มีปลาที่อ้างถึงเก็บเป็นรายการไม่เชื่อมได้ และแจ้งใน preview
ไม่สร้างปลาจำลองหรือสมมติรหัสผู้ให้ไข่/ผู้ให้เซลล์

ก่อนยืนยันต้องตรวจ:

- ข้ามแถวว่าง; CODE และ Specimen type ต้องครบในแถวที่มีรายการ
- No เว้นได้ หากระบุต้องเป็นจำนวนเต็มบวก ไม่ใช้สร้าง ID หรือจับคู่ปลา
- CODE ไม่ซ้ำในทะเบียนเดียวกัน; กลุ่มต้องเป็น CL/RT/DC/CLA และมีส่วนรหัสตามหลัง
- รหัสในช่อง CL/RT/DC/CLA ต้องตรงกลุ่มและหาได้ในทะเบียนที่ส่งมาหรือฐานข้อมูลเดิม
- CL/CLA ที่ถูกอ้างเป็นตัวอย่างของปลา ต้องไม่ถูกผูกกับปลาคนละตัวโดยเงียบ ๆ;
  RT/DC อ้างร่วมได้ และไม่นับเป็น specimen ใหม่ทุกครั้งที่ถูกอ้าง
- วัสดุที่ไม่รู้จัก รหัสชนกัน หรือชนิดวัสดุขัดกับข้อมูลเดิมต้องให้ผู้ดูแลตรวจ
  ไม่เปลี่ยนชนิดจากการเดา prefix
- ปฏิเสธรหัสตัวอย่างสาธิตที่มี EXAMPLE หรือ CLIENT_ รวมถึง fish/embryo key
  ตามกติกาเดิม แม้ข้าม Excel validation มาได้
- หากวางรหัสในแถว CONDITION/DATE/OBSERVER ให้แจ้งผิดตำแหน่ง ไม่ทิ้งข้อมูลเงียบ ๆ

preview ต้องแสดงปลา รหัส CL/RT/DC/CLA วัสดุ รายการใช้ร่วม และปัญหาที่ยังยืนยันไม่ได้
ข้อมูลว่างในไฟล์แก้ไขไม่ใช่คำสั่งล้างความสัมพันธ์เดิม

### 2. การบันทึกและความเข้ากันได้กับข้อมูลเดิม

สร้าง specimen หนึ่งรายการต่อ CODE และสร้างความสัมพันธ์แต่ละคู่เพียงครั้งเดียว
ยืนยันปลา ตัวอย่าง และความสัมพันธ์ใน transaction เดียว ป้องกัน retry สร้างซ้ำ
แยกยอด specimenCount ออกจาก linkCount ไม่บวก RT/DC ซ้ำตามจำนวนปลา

ใช้ specimen_kind และตารางเชื่อมที่มีอยู่ก่อน ไม่เพิ่ม source_type/source_code
หรือคอลัมน์บน clone_fish โดยอัตโนมัติหากใช้ความสัมพันธ์เดิมได้ครบ
ตรวจว่าข้อมูลเดิมที่มีทั้ง clone_fish_id และ link ไม่ถูกนับซ้ำ และไม่ทำให้ API/export
ตีความ RT/DC เป็นวัสดุที่เก็บจากปลาโคลน

การล้างค่า เปลี่ยนตัวอย่าง และ rollback ต้องมีเหตุผลและ audit; rollback งานหนึ่ง
ห้ามลบตัวอย่างที่ยังมีปลาอื่นหรืองานนำเข้าอื่นอ้างอยู่ ไม่แก้วันที่/อุณหภูมิเดิมเป็น null
เพียงเพราะแบบฟอร์มใหม่ไม่มีคอลัมน์เหล่านั้น

### 3. หน้าทะเบียนปลา

เพิ่มส่วน “ตัวอย่างที่เกี่ยวข้อง” พร้อมช่อง CL, RT, DC, CLA ทั้งตอนขึ้นทะเบียน
และแก้ไขปลา ให้เลือกทะเบียนเดิมหรือเพิ่ม CODE + Specimen type เมื่อมีตัวอย่างใหม่
แสดงบทบาทว่า CL/CLA เป็นตัวอย่างของปลาโคลน RT เป็นของผู้ให้ไข่ DC เป็นเซลล์ต้นแบบ
ไม่เรียก RT/DC ว่าเนื้อเยื่อของปลาโคลน

โหลดและบันทึกผ่าน API ที่ตรวจกลุ่ม รหัสซ้ำ ความสัมพันธ์ และสิทธิ์ผู้ใช้ที่ฝั่ง server
หากต้องเพิ่ม route สำหรับผูกตัวอย่างเดิม ให้กำหนดสัญญาใน OpenAPI และสร้าง types ใหม่
อย่าใช้ POST สร้าง specimen เดิมซ้ำเพื่อผูกกับปลาอีกตัว
ตรวจพฤติกรรม offline queue และการแก้ไขโดย member/admin ตามกติกาที่มีอยู่

### 4. Export และการทดสอบก่อนปล่อย

คงข้อมูลเสริมใน export เดิมไว้ ไม่ลบทิ้งเพราะแบบฟอร์มนำเข้าลดคอลัมน์
เพิ่มมุมมองที่ใช้ CODE และบทบาท CL/RT/DC/CLA ได้ตรงกัน พร้อมระบุรุ่นรูปแบบ
ไม่เรียก export ว่า import template จนกว่าจะทดสอบนำกลับเข้าได้จริง

กรณีตรวจรับขั้นต่ำ:

1. ปลา 2 ตัวใช้ CL คนละรหัสและ RT/DC ร่วมกัน: ได้ 4 specimens และ 6 links
2. ปลาไม่มี CL แต่มี RT/DC: ยอมรับโดยไม่สร้าง CL สมมติ
3. CLA จับกลุ่มถูกต้อง ไม่ตกเป็น CL; มีตัวอย่าง Anal fin clip และ left over cells
4. รหัสอ้างอิงหาย กลุ่มผิด CODE ซ้ำ วัสดุขัดกัน และข้อมูลผิดแถว: dry-run แจ้งตำแหน่ง
5. นำเข้าซ้ำ/retry/rollback ไม่สร้างซ้ำ ไม่ลบตัวอย่างที่ใช้ร่วม และ audit ตรวจย้อนกลับได้
6. ผลปลา 1=รอด/0=ตาย ผู้ตรวจรายครั้ง และวันที่ตรวจจริงยังถูกต้องหลังเลื่อนคอลัมน์ d
7. หน้าทะเบียนปลากรอก แสดง แก้ไข และอ้างตัวอย่างร่วมได้ตามสิทธิ์ รวมถึง offline
8. ข้อมูลเสริมเดิมและ export ยังอยู่ครบ และตัวอ่านรุ่นเก่าไม่อ่าน v4 ผิดแบบเงียบ ๆ
9. ไฟล์ v4 ไม่สร้างผล QC ไม่แสดงงาน QC บนเว็บ และข้อมูล/API QC เดิมยังอยู่ครบ

## ขอบเขตการปล่อยใช้งาน

รอบนี้ส่งเฉพาะ Excel คู่มือ ข้อกำหนด และแผน ไม่เปลี่ยน backend/frontend/database
ก่อนปล่อยต้องตรวจ image/commit และ migration ที่รันจริงบน production พร้อมทดสอบ
บนฐานข้อมูลทดสอบและข้อมูลลูกค้าที่ทำสำเนาภายในสภาพแวดล้อมที่ได้รับอนุญาต
ไม่ใช้การมีโค้ดใน main เป็นหลักฐานว่าฟีเจอร์กำลังเปิดใช้หรือมีข้อมูลจริงบน production

ไม่รวมระบบอัปโหลดรูป ผลตรวจ DNA ระบบตำแหน่งช่องแช่แข็ง หรือการออกแบบ LIMS เพิ่มเติม
